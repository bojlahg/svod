## Согласованный способ работы

- Архитектор исследует код, формулирует ограниченную задачу исполнителю, самостоятельно проверяет результат и возвращает конкретные замечания.

## Поведение, которое нужно сохранить

- Общие и проектные базы различаются по `brains.project_id`. Стабильный project ID уникален и неизменяем. Разные ID могут иметь одинаковое отображаемое название.
- Права токена задаются по каждой базе как `read`, `propose` или проектное `write`. Новые и старые токены без назначенных областей получают отказ. OAuth-вход без строки scoped-токена также получает отказ.
- Доступ вычисляется пересечением текущих прав пользователя и живых прав токена. Отзыв токена, удаление доступа и понижение пользователя до читателя учитываются при следующем обращении.
- Создание новой проектной базы требует отдельного флага токена. Повторный запрос возвращает уже доступную этому токену базу. Создание базы и выдача права создателю атомарны. Проверены конкурентные запросы одного ID и одинаковые названия разных проектов.
- Проектная заметка после прямой записи сразу читается по ID. Обновление сохраняет ID, ссылки на файлы и дату изменения. Общая база получает предложения новых заметок и правок существующих.
- Пока правка общей заметки ожидает проверки, принятую версию можно читать и искать. Предложения содержат атрибуцию токена, которая сохраняется после отзыва.
- Конкурентные изменения защищены **целочисленными ревизиями**. Миграция 0095 добавляет `revision`, `target_revision` и триггер увеличения ревизии. Проверки по строковому представлению Date ранее пропускали изменения в одну секунду.
- Перед принятием проверяются показанная ревизия предложения, исходная база и ревизия цели. При конфликте предложение сохраняется в очереди, пользователь видит ошибку и актуальный текст. Явное сохранение/rebase позволяет продолжить проверку.
- Принятие правки в той же базе обновляет исходную заметку с прежним ID. При переносе предложения-правки в другую базу создаётся новая заметка, исходная принятая заметка сохраняется. Это принятое архитектурное решение записано в плане.
- Папки, родители, заметки и цели предложений ограничены базой через SQL-ограничения, включая составные внешние ключи. Сохранять эти гарантии при импорте и индексации.
- Неизменённое сохранение, переименование папки и перемещение заметки сохраняют исходный Markdown, ID чанков и существующие векторы. Проверены BOM, LF, CRLF, одиночный CR, Unicode и пробелы в конце строк.
- Рендерер чтения и предпросмотра общий, поддерживает таблицы и подсветку кода. Сырые HTML-обработчики инертны, внешние картинки автоматически не загружаются.
- Поиск ограничен доступными активными заметками. Дедупликация результатов по заметке выполняется до итогового лимита, путь к папке возвращается вместе с результатом.

## Особенности production-форм

В Next `16.2.10` с React `19.2.4` наблюдался повторяемый сбой. Сервер сохранял данные, завершал HTTP 200 и возвращал успешный Flight-ответ, а клиент оставался в Saving либо показывал старое дерево. Однократный успешный прогон и добавление диагностических обработчиков меняли воспроизводимость.

Текущее решение для операций workspace использует обычный JSON-ответ и локальные состояния ожидания/результата. Текстовые операции отправляются как `application/json`, загрузка `.md` передаёт `File` через multipart. Native action остаётся в форме как существующий fallback. После успешного создания/переименования папки, переименования базы и перемещения заметки вызывается полное обновление текущей страницы. Редактор и загрузка сохраняют локальную обратную связь и обновляют маршрут.

Multipart-парсер удалял начальный UTF-8 BOM из строкового поля body. Передача текста через JSON устранила потерю. Файлы сохраняются через отдельное декодирование с сохранением BOM. При изменении транспорта повторить проверку исходных байтов.

Новый workspace-вход повторно использует `svod-actions`, проверяет cookie-сессию, права на базу и Origin, ограничивает поток запроса до 1 MiB перед разбором. UUID базы из маршрута определяет область операции. Origin учитывает Host и настроенные публичные URL, поскольку внутренний `req.url` Next мог содержать localhost при обращении через 127.0.0.1.

Сохранение предложения проверяющим отдельно ожидает `editProposalAction` и обновляет локальную ревизию. Ключ формы основан на ID предложения, чтобы обновление страницы сохраняло черновик и обратную связь. Токен-форма показывает реальный результат после окончания запроса, включая искусственно задержанный ответ.

Счётчик GitHub исключён из авторизованного layout, публичный запрос ограничен тайм-аутом. Это отдельное улучшение автономности интерфейса. Сходный внешний отчёт по зависанию приведён как диагностический контекст. [Next.js issue 97990](https://github.com/vercel/next.js/issues/97990)

## Исходное состояние embedding-сервиса

Это собственный FastAPI/SentenceTransformer-сервис в `services/embed/main.py`. Контракт — `POST /embed` с `{texts, kind}` для passage/query, `GET /health`, опциональный `/rerank`. BGE-M3 выдаёт 1024 нормализованных измерения.

Текущий Dockerfile использует `python:3.12-slim`, CPU torch `2.6.0`, sentence-transformers `3.4.1`, FastAPI `0.115.12`, uvicorn `0.34.0`. Файлы модели размещаются в `/models/bge-m3`. Текущий fetch скрипт скачивает resolve/main без полной идентичности модели, запуск Docker ждёт скачивания до uvicorn. Это точки переработки этапа 5.

`src/lib/embed.ts` направляет query на `EMBED_QUERY_URL`, passage на `EMBED_URL`, содержит тайм-ауты 10 и 120 секунд и пакет до 64. Сейчас проверяется в основном размерность. `embedHealthy()` допускает два ожидания по 15 секунд. Учесть это при готовности UI и worker.

`src/lib/chunk.ts` использует приблизительно 400 токенов, overlap 60 и минимум 40. Это прежний алгоритм по абзацам. Изменение заметки сейчас может заменять весь набор её чанков. Начать исследование общей синхронизации с `svod-notes.ts` и принятия в `svod-proposals.ts`.
